If you landed here from a 401

That was the point. Every endpoint except health, metrics and tenant bootstrap requires an API key, so an unauthenticated request gets 401 with an RFC 7807 body rather than a login page. Try it:

curl -i https://chronos-scheduler-o20q.onrender.com/v1/jobs

Try it for real

Tenant creation is deliberately unauthenticated — there is no key to present before the first one exists. It returns an API key and an HMAC signing secret, shown once.

curl -X POST https://chronos-scheduler-o20q.onrender.com/v1/tenants \
  -H 'Content-Type: application/json' -d '{"name":"you"}'

Then schedule something. Every delivery carries a stable idempotency key and an HMAC signature over the exact transmitted bytes:

curl -X POST https://chronos-scheduler-o20q.onrender.com/v1/jobs \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' -d '{
    "name": "hello",
    "schedule": { "type": "ONE_TIME", "runAt": "2030-06-01T12:00:00Z" },
    "target":   { "url": "https://example.com/hook", "payload": {"id": 1} }
  }'

And watch the SSRF guard refuse to fetch cloud instance metadata — the attack that turns a webhook scheduler into a credential exfiltration tool:

curl -i -X POST https://chronos-scheduler-o20q.onrender.com/v1/jobs \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' -d '{
    "name": "ssrf",
    "schedule": { "type": "ONE_TIME", "runAt": "2030-01-01T00:00:00Z" },
    "target":   { "url": "http://169.254.169.254/latest/meta-data/" }
  }'

The interesting part

Workers coordinate through a single atomic findAndModify against MongoDB. No leader, no queue, no lock service — scaling is adding containers and configuring nothing.

But the claim is only half of it. It stops two workers starting a job; it does nothing about a slow worker whose lease expired mid-delivery finishing one that has since been reassigned. So every terminal write re-asserts ownership, and a worker that lost its lease discards its result instead of overwriting whoever owns the job now. That is the difference between a duplicate delivery (fine, expected, deduplicable) and a corrupted schedule (not fine, and silent).
